# Axis

Axis is a personal organization application for iOS and Android, built with React Native, TypeScript, Expo SDK 57, and Expo Router.

## Development status

The application shell contains five tabs: Home, Tasks, Calendar, Finance, and Fitness. Tasks supports one-time tasks and fixed-schedule recurring tasks with occurrence history. Both support creation, editing, and soft deletion. One-time tasks keep their original completion/reopening behavior. Recurring occurrences can be completed, reopened, or skipped independently. Finance records actual income and expenses in BRL, provides Week, Month, and Year dashboards with category spending, manages planned Bills, Subscriptions, and Installments, and tracks work earned, received, and outstanding through Work Balance. Calendar integrates dated Tasks and financial obligations. Fitness supports an exercise library, routines, workout logging, and completed workout history. Home integrates today's actions, attention items, and the active workout with navigation into their owning features.

Tasks is stored offline in `axis.db` using Expo SQLite and Drizzle ORM. There is no account or cloud synchronization. Categories include six built-in choices plus custom categories that users can create and delete.

The main tabs live in `src/app/(tabs)/`. The root stack in `src/app/_layout.tsx` can host future detail screens outside the tabs. Shared UI lives in `src/components/`, with device-aware light/dark colors in `src/constants/theme.ts`. Feature UI, forms, and data access live under `src/features/`; database initialization and generated migrations live in `src/database/`.

## Run locally

Use Node.js 22.13 or later and npm.

```sh
npm ci
npm start
```

Open the development server in a compatible Expo Go app on an iPhone or Android device. Expo Go on iOS may require signing in to the same Expo account in the CLI and Expo Go. This is a development-tool requirement; Axis has no account flow.

```sh
npm run android  # Open an Android emulator or connected device
npm run ios      # Open the iOS simulator (requires macOS)
npm run lint     # Run ESLint
npx tsc --noEmit # Check TypeScript
```

## Database development

Database startup opens SQLite, enables foreign keys and WAL, applies bundled Drizzle migrations, and seeds default categories and Fitness exercises before mounting the app navigator. The native splash stays visible until startup succeeds or a retryable error screen is ready. Initialization never resets existing data on failure.

Schema changes belong in `src/database/schema.ts`. Generate a new migration with:

```sh
npm run db:generate -- --name=describe_change
npm run db:check
```

Review and keep the SQL, journal, snapshot, and generated migration bundle together. Do not edit migrations after shipping them. Migrations run locally on application startup; no database credentials or server are needed.

Tasks and categories use UUIDs and Unix timestamps in milliseconds. Dates use `YYYY-MM-DD` and times use `HH:MM`, preserving local calendar values rather than converting them to UTC. Time requires a date; clearing a date also clears its time. Priority defaults to `none`.

Deleting a custom category leaves its row and existing task references intact. It disappears from category choices, and its tasks display no category label. Tasks with no category also omit the label; the editor uses `No category` to select this empty state. Built-in categories have fixed IDs, are seeded without duplication or timestamp changes, and cannot be deleted through the feature.

## Recurring tasks

Use the editor's `Repeats` selector for Daily, Weekly, Monthly, or Yearly. A recurring task requires a start date and can have a time. Daily, weekly, and monthly patterns support positive whole-number intervals. Weekly patterns allow multiple weekdays; weeks begin on Monday, anchored to the week containing the start date. Monthly patterns use a selected day, clamped to the last valid day of shorter months. Yearly patterns use a selected month/day; February 29 becomes February 28 in non-leap years. `Ends` supports Never or an inclusive On date.

`task_recurrences` stores schedule versions with an inclusive `effectiveFrom` and exclusive `effectiveUntil`. Ordinary title, description, priority, and category edits apply globally. Schedule, start date, time, and end condition edits take effect **tomorrow in the device's local calendar**, keeping today's schedule and older history intact. `Stop repeating` uses the same boundary and keeps the Task and history. Choosing Does not repeat for an existing series also stops it; it does not turn its parent into a standalone task. Enabling recurrence on an existing one-time task starts no earlier than today and clears the parent's one-time completion field. After that, completion belongs to occurrences.

The Tasks view materializes a bounded window from 30 days before today through 30 days after today. It refreshes on focus, app resume, and a detected local day change. History loads 30-day pages of older dates on demand, using the schedule version that applied at the time. Initial creation with an earlier start date can therefore show missed occurrences, while older dates are generated only when requested. There is no unlimited future generation or background worker. Unique rule/date and active task/date indexes make generation idempotent across restarts.

`task_occurrences` stores scheduled local date/time, pending/completed/skipped status, completion time, UUIDs, and creation/update/deletion timestamps. Past scheduled dates and outcomes are never rewritten when a schedule changes. Obsolete future rows are soft-deleted; early completed/skipped outcomes remain visible in History as `Previous schedule`, without returning to the active schedule. Pending obsolete future rows are hidden. Deleting the parent soft-deletes only the Task and hides its occurrences while retaining stored history.

Missed is a display state derived from pending occurrences. Timed occurrences become missed after their local scheduled date/time; date-only occurrences become missed after that day ends. Completing a missed occurrence records completion normally. Reopening completed or skipped occurrences returns them to pending, without shifting future dates. Labels update every minute while Tasks is focused and immediately on app resume. Dates/times float with the device's current local time zone; they do not store a time-zone identifier or a UTC scheduled instant. DST arithmetic preserves intended calendar dates.

The main list shows occurrences instead of an additional parent task, with a separate Skipped group. Upcoming shows only the earliest pending future occurrence per recurring task, alongside every upcoming one-time task. Completing or skipping that occurrence reveals the next one; Earlier and Today retain all their occurrences. Recurring rows show a compact summary of the latest retained schedule beside the occurrence's date/time. The full bounded generation window remains stored. `Repeating tasks` provides access to schedules and history, including stopped series and starts beyond the upcoming window. History uses current Task properties rather than duplicating titles/categories into occurrences. Stage 4's additive `0001_recurring_tasks.sql` migration leaves existing Stage 3 Tasks and Categories unchanged.

## Finance ledger

Finance transactions record money that actually moved: income received or expenses paid. The editor requires Type, Amount, Description, and Date, with optional Category and Note. Dates default to the device's local calendar day; the editor and domain reject future dates to avoid entering planned payments. SQLite itself permits valid future civil dates. Planned obligations belong to Commitments; work receivables belong to Work Balance. There are no accounts, bank balances, transfers, currency selectors, or cloud synchronization.

All stored transaction amounts are positive integer centavos in `amountMinor`, with direction stored separately as `income` or `expense`. The supported entry range is 1 through `Number.MAX_SAFE_INTEGER` centavos (R$ 0,01 through R$ 90.071.992.547.409,91). `src/features/finance/money.ts` parses whole strings using integer arithmetic, and formats integer digits without floating-point currency rounding. Accepted Brazilian notation includes `123`, `25,90`, `25,9`, `1.234`, and `1.234,56`; outer whitespace and an optional leading `R$` are accepted. Letters, exponents, signs, dot decimals, malformed grouping, more than two decimal digits, zero, and unsafe amounts are rejected on entry. Display formatting also accepts zero, signed values, and BigInt totals beyond the entry limit for derived dashboard values.

`finance_transactions` stores UUIDs, type, amount, description, optional note/category reference, a `YYYY-MM-DD` transaction date, and epoch-millisecond creation/update/deletion timestamps. Active rows are ordered by transaction date descending, creation time descending, then ID for stable ties. SQLite constrains type, integer centavos, nonempty descriptions, civil dates, timestamps, and category/type compatibility. Deleting a transaction creates a tombstone after confirmation; there is no Trash screen.

Finance categories are separate from Task categories. Built-in expenses are Housing, Food, Transport, Shopping, Health, Pets, Entertainment, Utilities, Subscriptions, and Other. Built-in income categories are Salary, Freelance, and Other. Startup seeds thirteen fixed UUIDs idempotently without changing existing timestamps or reviving tombstones. Built-ins cannot be archived through the feature. Users can create typed custom categories through Categories or the editor's final `+ New category` action. Inline creation saves and selects the category before returning to the editor; changing Type clears an incompatible selection.

`Archive` soft-deletes a custom Finance category using its existing `deletedAt` field, preserving every existing transaction reference and timestamp. Historical transaction rows continue showing the category's original name, with no Uncategorized label. Finance reads retain archived categories for historical name resolution and future category grouping; category selectors and management show only active categories. Transactions without a category still omit the label. A replacement category with the same name gets a new identity and does not inherit the archived category's transactions.

When editing a transaction with an archived category, the selector displays `Category name (archived)`. Opening the selector shows the retained current category as explanatory text, followed by active choices and `No category`; the archived category is not a selectable option. Cancelling keeps it, saving other fields keeps it, and choosing an active category or `No category` changes it explicitly. Re-selecting the current transaction type also preserves it; changing to the opposite type clears an incompatible reference. New assignments always require an active category of the correct type. The existing composite foreign key continues to enforce category/type compatibility. Tasks retain their separate deletion/display semantics.

The additive `0002_finance_ledger.sql` migration creates only Finance tables and indexes. Existing Tasks migrations, tables, recurrence generation, and occurrence history remain intact. The Tasks form controls and calendar helpers now live in shared `src/components/form-controls.tsx` and `src/utils/calendar.ts`, with compatibility exports for Tasks: Finance uses the same accessible selectors, themed fields, local-date validation, and native picker conversion. Tests share the existing Node SQLite/Expo Drizzle statement adapter in `tests/helpers/database.ts`; production data-access factories stay feature-specific.

## Finance dashboard

Finance opens on Dashboard with the current Month selected. A compact Dashboard / Transactions selector keeps the existing full ledger accessible; Add transaction and Categories are available from either view. Transactions retains its existing ordering and editing/deletion behavior and is not filtered by the dashboard period.

The dashboard offers exactly Week, Month, and Year. Week is Monday through Sunday, Month uses the actual first and last day of the calendar month, and Year is January 1 through December 31. All bounds are inclusive local `YYYY-MM-DD` business dates. Previous/next controls navigate historical periods; next is disabled in the current period, and a Current period action returns directly from history. Choosing a different period kind starts at its current period. Navigation is React UI state, never persisted. While Finance is focused, app resume and a detected local day change refresh the data; current selections advance across calendar boundaries while historical selections remain selected.

Exactly three summary cards share the selected range: Income, Expenses, and Net Flow (`Income - Expenses`). `periods.ts` handles civil-date bounds and navigation with explicit reference dates. `analytics.ts` filters active transactions in SQLite using the existing partial date index and projects only type, centavos, category ID, and category name. It aggregates the selected rows with BigInt centavos rather than SQLite `SUM` or floating-point monetary arithmetic, preserving exact totals even beyond the safe Number range or SQLite's signed 64-bit sum limit. The dashboard query does not load the entire ledger. There are no stored summaries, new tables, migrations, or caches.

Spending by Category includes only expenses, groups by category ID, and sorts the largest totals first. Archived categories retain their names and remain separate from replacement categories with the same name. Genuinely unassigned expenses use `No category` in this breakdown only; normal transaction rows keep omitting an absent category label. Every expense contributes to a group, so category totals reconcile exactly with Expenses. Horizontal native bars show each group's share of Expenses; the display-only ratio never alters money. Names and exact BRL amounts wrap, and each accessible category row announces both. Zero expenses shows no bars, empty periods show three zero values, and expense-only periods show negative Net Flow.

The dashboard does not add previous-period comparisons, Savings Rate, Work Balance, accounts, budgets, or multi-currency support. Planned Commitments do not affect its totals until an actual payment creates a ledger Expense.

## Finance commitments

Finance's internal selector provides Dashboard, Transactions, and Commitments without adding a bottom tab. Add transaction and Categories remain available from every view. Commitments distinguishes Bill, Subscription, and Installment in creation, rows, and details. Each requires a title, positive expected BRL amount, and first due date; Installments additionally require 1–1200 payments. A category is optional and must be an Expense category. Existing archived references retain their names and can be kept while editing, but archived and Income categories are not selectable for new assignments.

Bills and Subscriptions use one shared monthly schedule engine. The first due date anchors the billing day; day 29/30/31 clamps to a shorter month's last day without changing the intended day in later months. Installments use the same engine with a finite count and immutable logical indices. There is no end-date input for installments, no partial payment model, and no authoritative paid-count counter.

`finance_commitments`, `finance_commitment_schedules`, and `finance_commitment_occurrences` are added by `0003_finance_commitments.sql`. Previous migrations and existing table definitions remain unchanged. An additive unique `(id, type)` index on Finance transactions supports an Expense-only payment foreign key. Occurrences also reference their parent and schedule version, with unique parent/date, installment-number, and payment constraints. All identities are UUID strings. Parent title/category stay on the commitment; expected centavos are snapshotted on occurrences and schedule versions. Status checks keep Paid linked to one Expense and require Pending/Skipped to have no payment link.

Generation is idempotent and catches up every historically scheduled due date through today, for active, paused, ended, and completed commitments. Internal twelve-month batches cover each schedule's effective interval, excluding paused periods and stopping at its ending boundary or final installment. Existing occurrence identities, expected amounts, and outcomes are retained. Details / History pages older Paid/Skipped outcomes in twelve-month periods; pending obligations are always included regardless of age, without requiring History paging to materialize them. Normal Upcoming computes previews within the current and next two calendar months and shows only the next pending future date per active commitment. Future previews are persisted only when Paid or Skip is confirmed, or when their due day arrives. This avoids pre-creating future obligations that would have to be erased on Pause. Future-start series beyond the preview window remain manageable through their parent details. There is no background worker or unlimited future generation.

Overdue is derived from `pending` and `dueDate < today` using local civil dates. It is never stored, moved forward, merged, or automatically resolved. The Overdue count and list include every unresolved past obligation, including those older than twelve months, and each has Paid/Skip actions. All overdue/current obligations remain distinct; the same commitment can also have one Upcoming preview. Focus, foreground resume, and detected local day changes refresh the view and catch up missing due dates.

Paid opens confirmation with the occurrence's expected amount and today's payment date. Both can be changed; the actual amount must be positive and the date must be today or earlier. Confirmation atomically materializes the occurrence if needed, inserts an Expense with the actual centavos/date and commitment title as its description, links it, and marks it Paid. A retained archived Expense category remains valid for this existing commitment's payment. The original expected amount is never overwritten with the actual payment. Skip creates no transaction, resolves only that occurrence, and remains in History; Reopen reverses a skipped outcome.

Linked payment transactions remain editable through Transactions, including actual amount/date/category/description/note; their type must stay Expense. History and Total paid read their current actual values. Their Delete action is omitted and the data layer rejects ordinary deletion or conversion to Income. Use Undo payment in Commitments history instead: one database transaction soft-deletes the linked Expense and reopens the occurrence as Pending with its expected amount intact. The Expense immediately leaves dashboard totals. The old transaction remains stored as a tombstone; another payment can subsequently be recorded. Failures roll back both sides. Undo/Reopen of a completed installment series makes it Active again.

Pause catches up all due dates through today, closes open schedules after today, and retains every existing occurrence unchanged. Closed schedule versions exclude paused months during every subsequent catch-up. Resume opens a date confirmation with the next date implied by the previous billing day, after any retained future occurrence. Keeping the proposed date retains the intended billing day even if February clamps it; selecting a different date establishes the new monthly anchor. Retained overdue dates remain unresolved. New installment scheduling continues after both retained indices and elapsed historical indices, so catch-up cannot restart numbering. If every installment already has a due date, Resume is unavailable; resolve those outstanding obligations through Paid or Skip.

Title, category, and expected amount can be edited. Type, installment count, and the anchor stay fixed in ordinary editing; use Pause / Resume for a new anchor. Amount changes apply to future pending occurrences after today through a new schedule version. Past and resolved expected amounts remain unchanged, including older pages loaded later. Bills and Subscriptions can be Ended; this closes future scheduling after today and preserves unresolved obligations, prior outcomes, and all schedule history. They remain in History and can still have past obligations Paid or Skipped.

Installment progress counts Paid and Skipped as resolved. Remaining is the configured count minus resolved outcomes, including not-yet-materialized installments. Resolving the final installment automatically marks its parent Completed and moves it into History. Total paid uses BigInt centavos from actual linked Expenses, so skipped installments add nothing and actual-vs-expected differences remain visible. No commitment action adds an Expense except a confirmed payment.

Stage 7 does not implement partial payments, reminders/notifications, planned-vs-actual analytics, Work Balance, accounts, budgets, multi-currency, or cloud synchronization.

## Work Balance

Finance → Work tracks the current Work dataset independently of the dashboard's Week/Month/Year period. Work creates an amount earned, never a ledger Income by itself. Only **Record payment** creates actual Income. The summary shows Earned, Received, and Outstanding, with derived totals by Client. Any positive Outstanding balance, including partial payments, stays in Outstanding or Payment overdue. Work enters History only at zero Outstanding; received payments remain independently inspectable in History, displayed in batches of 20. Entry details show compensation, balances, expected payment date, and allocated payments.

The UI consistently calls this name-only entity **Client**. Internal `WorkCounterparty`, `counterpartyId`, and `work_counterparties` names remain unchanged to avoid a cosmetic database migration. Work and payment Client fields use the reusable anchored `AutocompleteField`. Empty searches show no historical list. Matching ignores case, accents, and repeated/outer whitespace; prefixes sort before substrings, then normalized alphabetical name and ID. At most eight suggestions appear. A nonempty query without an exact active match offers `+ Create "Name"` in the same overlay; successful creation selects the ID and closes it, while errors preserve the query. No extra modal or persisted usage counter is used.

Client management supports creation and Archive. Archival retains all references/names, excludes the Client from new-work suggestions, and allows its outstanding historical work to receive payment through payment autocomplete. Opening/editing an old entry retains its archived Client until explicitly changed; a Client with active payments is locked to protect combined-payment grouping. Recreating an archived name creates a different ID.

`work_entries` stores exactly Hourly or Fixed compensation, selected through the shared `SegmentedControl`. Hourly entries store positive integer duration minutes and a positive integer centavo rate/hour; Fixed entries store a positive integer centavo amount, with no fake hours/rate. Terms are historical facts on the entry, with no counterparty default-rate lookup. Hours/minutes inputs are parsed with BigInt into whole minutes. Hourly Earned uses `(BigInt(minutes) * BigInt(rate) + 30n) / 60n`: nearest centavo, exact halves rounded up. Intermediate products and aggregate sums never use floating-point money. Individual earned/payment values are bounded to `Number.MAX_SAFE_INTEGER` centavos; aggregate balances may exceed that limit using BigInt. Tiny hourly work that rounds to zero is retained as settled with **No payment due**, creates no Income, and remains inspectable in History.

Work dates, optional expected dates, and receipt dates are local `YYYY-MM-DD` strings. Work records actual work, so its date must be today or earlier. An expected payment date may be past or future; it never becomes a ledger date automatically. Unpaid/Partially paid/Paid are derived from allocation totals, with equality to Earned taking precedence for zero-centavo entries. Payment overdue requires a positive Outstanding and an expected date strictly before local today. Focus, resume, and local-day refresh use the existing Finance lifecycle.

`work_payment_allocations` provides the many-to-many relationship between Work entries and Finance Income transactions. There is no separate Work payment table or persisted aggregate/status. Record payment selects one counterparty and one or more of its outstanding entries; each selected allocation defaults to Outstanding and can be reduced. The payment total is derived from positive centavo allocations, never separately entered. The category selector accepts active Income categories, No category, and inline `+ New category` automatically typed as Income. A receipt creates one Income transaction and all allocations in one immediate SQLite transaction. Its initial description is the counterparty name; its amount is the allocation sum and its date is the chosen receipt date. Multiple receipts can pay one entry, and one receipt can cover several entries. No allocation may exceed remaining Outstanding or mix counterparties.

Work-linked Income rows are labelled in Transactions and have no ordinary Delete action. Their normal Finance editor locks Type/Amount while allowing date, description, note, and compatible category edits, including retaining a historical archived category. The Finance data service also enforces Income and exact allocation-total equality inside a transaction. **Undo payment** in Work details/History atomically soft-deletes the Income and all of its allocations, retaining their historical rows. A combined payment's Undo affects every entry covered by that payment; confirmation states that scope. Incorrect allocations are corrected by Undo and recording the receipt again. Other receipts remain intact.

Work edits may change compensation as long as Earned remains at least Received. Changing a counterparty with active allocations is blocked. Confirmed soft deletion is allowed only after all active allocations have been undone; it never physically deletes financial relationships. Work reads validate Income linkage, reconciliation, same-counterparty grouping, and entry bounds, reporting inconsistencies rather than silently hiding debt. The additive `0004_work_balance.sql` migration adds three tables, foreign keys, positive/integer compensation/allocation checks, active name uniqueness, and indexes for counterparties, work/expected dates, and both allocation links. Earlier migrations and existing data remain unchanged.

Stage 8 excludes recurring work/salary, timers, invoicing, taxes/payroll, overpayments, accounts, CRM metadata, cloud sync, and complex Work period analytics. SQLite integration tests exercise the actual Drizzle driver and feature APIs, including failed payment/Undo/migration rollback, prior-stage preservation, restarts, and foreign-key/integrity checks. Form tests render the real web branches with the shared menu host; only the unavailable native date-picker boundary is stubbed. Native export success does not replace device validation.

For Stage 8 device validation, create Hourly and Fixed entries and confirm Finance Income stays unchanged. Test counterparty inline creation/Cancel/duplicate errors with the keyboard, archive a client and pay its historical debt, record partial and combined receipts, and verify the one-row Income total/category/date. Check locked Income type/amount, safe Finance edits, Undo of a combined payment, earned-below-received rejection, protected deletion, History paging, offline restart, expected-date overdue refresh, both themes, larger text, and VoiceOver/TalkBack. Physical-device testing has not been performed for Stage 8.

## Shared form interactions

`SegmentedControl` in `src/components/form-controls.tsx` keeps small primary choices visible: Transaction Type, Commitment Type, and Finance category Type. It accepts `label`, `value`, `options`, `onChange`, and optional `disabled`; selected segments have a checkmark as well as the existing selected color. Locked commitment kinds and linked-payment transaction types remain locked.

`SelectField` accepts `label`, `value`, `options`, `onChange`, optional `displayValue`/`description` for retained archived values, and an optional final inline `action` with a title and content renderer. It is used for Task, Transaction, and Commitment categories; Task Priority; and the existing recurrence frequency/month/end choices. Finance supplies active categories of the correct direction, while Tasks supply their independent categories. `No category` remains available. Archived Finance references are displayed as `Name (archived)` without becoming selectable or being cleared on opening the editor.

All three category dropdowns offer `+ New category`. This switches the **same anchored overlay** to `InlineNameForm`, with a required Name and Create/Cancel actions. Transaction creation inherits Expense or Income from its draft; Commitment creation always uses Expense; Task creation uses its separate domain. There is no additional type prompt. Features supply their existing creation callbacks and error formatters: validation/persistence are authoritative, options refresh through the existing feature reload, and success selects the saved ID before closing and focusing the original Category field. The parent editor remains mounted with its draft and scroll position intact. Broader category managers remain available.

Cancel discards the unsaved name/error and returns to the options in the open menu, preserving the previous selection. Tapping outside, Escape, accessibility escape, or modal Back closes the menu and discards the unsaved name/error without saving; reopening starts with options. Errors retain the creation form and name for correction/retry. Opening another dropdown replaces the current interaction.

Each `AdaptiveModal` provides a transparent native modal and one full-window `FormSelectionHost` outside its sheet and scrolling content. Both host and trigger are measured in window coordinates, so sheet offsets and scroll position are accounted for. Menus can extend beyond a short sheet, while their usable bounds still respect safe-area edges and the keyboard. The overlay chooses below or above the field and clamps to usable bounds without expanding the form. Options, autocomplete, and inline creation measure their own content. Keyboard events, sheet/host layout, window changes, and font scaling refresh placement. Available height is the smaller of the modal host and keyboard boundary, avoiding double keyboard subtraction. During text entry, a covered trigger is clamped into those bounds so the menu stays open. Autocomplete keeps its search input above independently scrolling results; category creation keeps Create/Cancel outside its scrolling body. `FormScrollView` prevents underlying form gestures while a menu is open.

`AdaptiveSheet` separately measures its fixed header and natural scroll content. Its height is the lesser of header + body + bottom safe-area padding and the maximum usable height. The bottom stays fixed at the viewport bottom; short/medium content moves only the top edge, while long content reaches the safe top boundary plus a small theme gap and its single body scrolls. The sheet background covers the entire bottom safe area and viewport width, with square bottom corners; the content retains its maximum width and safe horizontal padding. The parent page can be visible above the sheet, never below it, and the native modal blocks underlying navigation interaction. Changes to errors, sections, payment history, and text size update the natural height. The initial measurement is hidden to avoid a flash of a mostly empty full-height sheet. Keyboard events anchor the sheet directly to the effective keyboard/window boundary, remove redundant home-indicator padding while the keyboard is open, and keep focused shared inputs visible. Hiding the keyboard restores the physical bottom anchor and natural height. Tasks editors, recurring management/history, Task/Finance category managers, Transaction editors, and Commitment/Work editors/details/history share this infrastructure. Screen navigation stays unchanged.

Shared `FormField` inputs with `editable={false}` expose disabled metadata and use muted text/reduced emphasis consistent with protected segments. Work-linked Amount includes “Amount is controlled by the linked Work payment.” Type/Amount remain protected by the existing domain rules; safe transaction fields remain editable.

Only one dropdown can be open. Selection, success, or dismissal restores focus to the field; Cancel focuses the options heading. Controls announce their context, current selection, required name, errors, and action labels. On web, Escape dismisses and Tab stays within options or the inline form. Arrow/Home/End keys move focus in options and retain normal text-editing behavior in the name field. Date/time pickers, weekday controls, confirmation dialogs, and schedule/business rules are unchanged. Validate keyboard placement, modal stacking, bottom-of-screen fields, larger text, and VoiceOver/TalkBack on physical devices; automated rendering/export checks do not replace those checks.

## Stage 9 Calendar integration

Calendar projects dated one-time Tasks, actual recurring Task occurrences, unresolved Commitment due dates, and Work entries with an expected payment date and positive Outstanding. Ordinary ledger transactions stay in Finance. Calendar items are derived in memory; there is no Calendar table, duplicated source ownership, migration, or new dependency.

The month opens with local today selected and uses Monday–Sunday weeks. Previous/next navigation preserves the selected day number and clamps shorter months; Today resets both month and date. Leading/trailing dates are selectable and move context to their own month. Populated dates show one compact source dot in stable Task, Commitment, Work payment order, never one dot per record or a numeric badge. The centralized `calendarTask` (blue), `calendarCommitment` (amber), and `calendarWorkPayment` (teal) theme tokens have temporary light/dark variants. Marker presence and actual per-source counts are derived in `markers.ts`; date accessibility labels announce those counts, while decorative dots are hidden from assistive technology. A fixed marker strip keeps rows independent of record count, with no unused source slots. Today's date remains underlined and selection outlined. The selected-day agenda orders timed Tasks by time, then all-day Tasks, Commitments, and expected Work payments; title and source identity break ties. Only populated sections render. Empty days show “Nothing scheduled for this day.”

`src/features/calendar/data.ts` coordinates public bounded `readRange` APIs from the source modules, and `projection.ts` maps their results into a discriminated presentation model. The requested range is the displayed grid, including adjacent days, and public range requests cannot exceed 62 days. Existing date indexes serve the reads. Task recurrence uses the existing generator and unique identities to persist only requested occurrences. Commitment due dates through today are materialized for the requested range with the existing schedule rules. Future Commitments use the same bounded schedule previews as their normal source list: browsing a distant month does not reserve installment numbers or move a future resume anchor. Paid/Skip can resolve one validated preview beyond the normal three-month list window without generating intervening future dates. Historical versions, pause gaps, end boundaries, installment limits, tombstones, and outcomes remain authoritative.

Completed one-time Tasks remain on their original date; recurring outcomes use existing Completed/Skipped/Missed derivation. Calendar Complete/Reopen delegates to the Task service after resolving the latest stored outcome. Tasks retain their category display rules; Finance's archived category names remain meaningful. Commitments keep overdue dates on the original due date and omit Paid/Skipped rows. Work uses the existing earned/allocation reconciliation and shows remaining Outstanding after partial receipts; fully paid entries disappear from unresolved Calendar projection. A range-scoped Work read validates an entire combined receipt, including its related entries outside the month, without scanning unrelated Work/payment history.

Tapping a row pushes the `calendar-source` Expo Router route, which launches the existing Tasks or Finance screen with its existing editor/detail sheet opened. The selected Commitment obligation is placed first in its history sheet, including distant future previews and older overdue dates. Paid, Skip, Pause/Resume, edit/history, and Work Record payment remain implemented by those source flows. The stack's Calendar back action returns to the mounted Calendar with its month/date preserved. Returning to Calendar, foreground resume, local-time refresh, and Calendar Task actions reload the visible projection. All launched dialogs reuse the shared bottom-anchored adaptive sheets.

Stage 9 includes no standalone events, arbitrary appointments, external calendar sync, or reminders/notifications. ## Stage 10 Fitness foundation

Fitness has Workout, Routines, Exercises, and History views inside the existing tab. An unfinished workout has a prominent Resume action in every view. Start from an active routine or start a free workout. A second start offers Resume; it never replaces the existing session. The data service also returns the current session, and a partial unique SQLite index prevents a second active row. Confirmed Finish records completion even with fewer than planned sets (or an empty workout); confirmed Discard soft-deletes the session without changing its routine.

The library seeds fourteen exercises with fixed string IDs and all four measurement types. Custom exercises require a normalized, nonempty name of at most 120 characters and a type, selected with the shared anchored SelectField. Active duplicate names are rejected case-insensitively, consistent with SQLite's existing name rules. Built-ins cannot be archived through Fitness. Archiving a custom exercise removes it from new choices while retaining references; a replacement with the same name has a new ID. Archived library entries and routines remain inspectable. Exercises already in an active workout can still be logged after archival.

Routines contain ordered entries with optional planned set count (1–100), optional rep ranges for Strength/Bodyweight, duration for Duration, and distance for Distance. Move up/down preserves entry IDs; removal is soft. Existing archived exercise references remain in their routines and are visibly marked; they are omitted when starting a new workout. Starting from a routine snapshots its name and every active entry's exercise identity, display name, type, order, and targets into session-owned rows. Renaming/reordering/removing/archiving source definitions cannot rewrite active or completed performance.

Only ordinary sets are supported. Strength stores required nonnegative integer weight grams and positive integer reps. Bodyweight stores positive integer reps and optional positive added-weight grams; null means ordinary bodyweight, with no body-weight measurement. Duration stores positive integer seconds. Distance stores positive integer meters and optional positive integer seconds. Inapplicable fields stay null. Weight inputs use kg; distance inputs use m/km; durations use minutes plus 0–59 seconds. Strict decimal strings accept a dot or comma and at most three fractional digits for kg/km. BigInt scaling precedes safe-integer conversion; signs, exponents, grouping, excess precision, fractions of meters/reps/seconds, and overflow are rejected. SQLite separately enforces typed fields, safe integer bounds, foreign keys, and active ordering.

Planned counts remain session targets, with a next-set action and logged/planned count in the UI. No empty performance rows are persisted. The set editor offers the previous logged set's values for quick entry, then validates and saves actual values. Set IDs remain stable through editing; deletion is soft and visible numbering renumbers naturally. Adding/removing session exercises never changes the routine.

Session exercise notes and an optional workout note are trimmed, clearable, and limited to 2000 characters. Completed sessions are read-only in both the UI and mutation APIs. History orders completed workouts newest first, initially loads twenty summaries, and loads older summaries on demand. Detail shows the snapshotted exercises, actual sets, and notes rather than replacing performance with current routine targets. Active and discarded sessions stay out of History.

Fitness reuses shared AutocompleteField, SelectField, SegmentedControl (active/archived and distance unit), AdaptiveModal, and AdaptiveSheet. Autocomplete searches active custom/built-in exercises and offers a richer Create action via the optional `onRequestCreate` callback; existing simple `onCreate` consumers retain their behavior. The search overlay closes before the exercise creation sheet replaces content inside the same native modal. Cancelling that creation form returns to the parent editor; successful creation persists, refreshes choices, adds the exercise, and returns with the routine draft intact.

The additive `0005_fitness_foundation.sql` migration creates six Fitness tables; previous tables, migrations, and feature business rules are unchanged. Startup seeds the library idempotently. Tests exercise real Drizzle/SQLite queries, numeric limits, archival, snapshot independence, one-active enforcement, set/note lifecycle, paged read-only history, restart, preservation of every earlier table and Calendar projection, migration rollback/retry, and foreign-key/integrity checks. Component integration tests use the existing web renderer and exercise real form callbacks; they do not simulate native gestures.

Stage 10 excludes special set types, rest timers, PR/1RM analytics, charts, body measurements, workout scheduling/Calendar integration, notifications, HealthKit/Apple Health, calories/nutrition, nonmetric units, and cloud sync. Physical testing has not been performed. On iPhone Expo Go, verify routine/free starts, second-start Resume, rapid decimal set entry (dot/comma), unit changes, keyboard focus, exercise autocomplete and Create/Cancel, long routines and Move up/down, removal confirmations, notes, Finish/Discard, restart offline, read-only History, both themes, larger text, and VoiceOver. Repeat Android keyboard/menu and TalkBack checks.

## Stage 11 Home integration

Home answers what needs attention today using source-owned data. It stores no cards, counts, summaries, or copied records. Today includes pending one-time/recurring Tasks, unresolved Commitment occurrences due today, and Work entries with payment expected today and positive Outstanding. Ordinary Finance transactions, future/undated tasks, resolved outcomes, and discarded workouts are excluded. No monthly Finance statistics are shown; the Finance Dashboard remains their home.

Calendar and Home share the source/date item model and projection in `src/features/scheduled-types.ts` and `scheduled-items.ts`. The existing Calendar projection exports stay compatible. Home's data layer calls the existing Tasks, Commitments, Work Balance, Finance category, and Fitness read APIs; it does not calculate recurrence, money, or schedules independently. Normal source-owned bounded Task generation and complete due-Commitment materialization remain unchanged. Repeated reads do not duplicate occurrences or create Home data.

Today orders timed Tasks, date-only Tasks, Commitments, then expected Work payments using the shared deterministic comparison. It previews at most five Tasks, three Commitments, and three expected Work payments. Needs attention previews at most three per source: Tasks by priority then most recent original date/time, and financial obligations by most recent original date. Every preview reports the full relevant count and offers a remaining-item/View all action when truncated. Full lists stay in the owning modules; old unresolved Commitments still count even when outside the preview.

One-time Tasks reuse the existing Earlier group for past dates; an elapsed time today does not create a new one-time Missed rule. Recurring occurrences reuse `occurrenceState`, including its exact time and date-only boundaries. A missed occurrence scheduled today moves to Needs attention rather than appearing twice. Task attention follows the existing normal 30-day occurrence window; this stage does not backfill unlimited recurring Task history. Commitment due dates and Work expected dates never move to today. Archived Finance names remain historical metadata, while archived Task category labels remain omitted.

Task rows have a quick Complete action that re-reads the exact source date/occurrence identity and invokes the existing Task API. Repeated taps cannot reopen a completed item, and stale skipped outcomes are retained. Reopening, Paid/Skip, and Work payment recording remain in the owning feature. Home and Calendar share a source-screen adapter: the existing Task editor, Commitment detail/payment sheet, Work detail/payment sheet, and Fitness workout sheet open through source identity. Home's route uses a Home back title; Calendar retains its Calendar back title. Fitness accepts an initial session ID, opening the requested active workout or read-only completed session without creating another workout.

An active workout appears before the item previews with Resume. When none is active, Home may show the most recently completed workout if its completion timestamp falls on the current local day. It does not show workout metrics or analytics. Empty Home says “Nothing needs your attention right now.” and avoids empty module cards. Quick access is limited to View Calendar; the existing bottom tabs supply the other major shortcuts.

Refresh runs on tab focus, foreground resume, and every minute while focused. Each read freezes one local instant for all source queries, preventing a cross-midnight read from mixing days. Blur removes listeners/timers and ignores late callbacks. Failed reads clear stale summaries and show Retry. Existing themes, wrapping text, 44-point touch targets, section headings, and contextual source/status/date/amount accessibility labels are reused. Overdue and Missed are expressed in text.

Tests cover source ordering, actual recurrence identity, exclusions, historical overdue dates/counts, paused/ended commitments, preview limits, archival metadata, exact navigation targets, completion/payment/finish refresh, lifecycle cleanup, local midnight/time zones, idempotent reads, and real Home component callbacks. Calendar's existing projection/component tests continue to cover compatibility. No dependencies, database schema, migrations, notifications, Home customization, full-feature editors, or visual redesign were added.

Physical-device testing has not been performed. On iPhone Expo Go, check busy and empty Home, remaining-item links, old overdue obligations, active Resume and completed-workout links, source sheets and the Home back flow, quick completion, return after Paid/Skip/Work payment/Finish, midnight/app resume, long names, light/dark themes, larger text, and VoiceOver. Repeat Android navigation, wrapping, and TalkBack checks.
